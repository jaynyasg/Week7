## Vision

Career Quest Campus should become a safe, classroom-friendly career party game: quick toy challenges across a living campus, visible avatar rewards after each room, more career end paths, and a reveal ceremony that feels like a personality celebration instead of a plain score screen.

The win is not "more rooms" by itself. The win is a fast loop where the player tries a weird little career toy, earns a visible identity piece, watches the campus grow, and later sees those choices become a joyful Career DNA ceremony.

### 10x Check

The 10x version of this expansion feels like "Mario Party for careers," but age-safe and school-friendly:

1. Every room is a toy challenge with a distinct verb: drag, sort, match, build, remix, diagnose, rescue, compose.
2. Every result feeds the same trusted systems: `MiniGameResult`, `GameSession`, Career DNA, gallery, reveal, and campus evolution.
3. Every challenge gives a visible reward, so progress lives on the avatar and in the world, not only in a menu.
4. Career outcomes expand from five narrow paths into a broader set of positive possibilities.
5. The reveal ceremony synthesizes traits, badges, accessories, combos, and career families into a memorable identity moment.
6. The first build remains achievable because the implementation is data-driven, compact, and built on the existing persistent-scene architecture.

## Implementation Shape

### Data Spine

Create a small station definition layer instead of adding more switches to `OptionalRoomController`.

Implementation format decision: first-wave station content should live in static C# definitions, not ScriptableObjects or JSON. This is the fastest fit for the current codebase, easiest to unit test, and avoids editor/content-pipeline work before the toy loop is fun. ScriptableObjects can be a later migration if station count grows.

Minimum fields:

- `Id`
- `DisplayName`
- `VerbTags`
- `Prompt`
- `ToyPatternId`
- `Objects`
- `SuccessRule`
- `TraitDeltas`
- `AccessoryRewardId`
- `CareerTags`
- `BadgeArtKey`
- `CampusArtKey`
- `EvolutionPropAssetId`
- `Seeds`

Each seed should be small:

- `SeedId`
- `PromptOverride`
- `ObjectOverrides`
- `TargetRule`
- `ResultSummary`
- `NpcReaction`

Implementation schema contract:

- `PartyStationDefinition`: `Id`, `DisplayName`, `VerbTags`, `ToyPatternId`, `GuideName`, `GuideVoice`, `Prompt`, `Objects`, `SuccessRule`, `TraitDeltas`, `AccessoryRewardId`, `CareerTags`, `BadgeArtKey`, `CampusArtKey`, `EvolutionPropAssetId`, `Seeds`.
- `PartyStationSeedDefinition`: `SeedId`, `DisplayName`, `PromptOverride`, `ObjectOverrides`, `TargetRule`, `IntroLine`, `HintLine`, `EscalationHintLine`, `SuccessLine`, `RewardPreviewLine`, `ResultSummary`, `NpcReaction`.
- `PartyStationObjectDefinition`: `ObjectId`, `DisplayName`, `Role`, `SpriteKey`, `TargetId`, `ReactionKey`, optional `TraitHint`.
- Supported object `Role` ids for this plan: `CoreTask`, `Clue`, `Helper`, `Wildcard`, `Reaction`, `Bonus`, `Meter`.
- Supported first-pass `ToyPatternId` values: `DragToSlot`, `SortToBin`, `PickMatchingTrio`, `SequenceCards`, `ComposeSet`, `MatchAndCare`, `BalanceMeters`.

The seed bible can use playful prose such as "compose plus match" or "match plus care pattern," but implementation data must map each station to one supported `ToyPatternId`. Definition validation should fail on unknown pattern ids, unknown object roles, duplicate object ids, duplicate seed ids, missing guide copy, missing result copy, and seed overrides that reference unknown objects.

The existing `MiniGameResult` remains the output contract. The station system should emit ordinary activity results, not invent a parallel progression channel.

Result/presentation split: `MiniGameResult` and `GameSession` best results remain the scoring, reveal-readiness, badge, and Career DNA contract. Add a lightweight session-only reward event log for presentation facts that are not the same as "best score": recent station completions, selected seed id, seed-aware micro-result summary, top trait highlights, unlocked accessory id, and shown combo spark ids. Replays can append a recent reward event even when they do not replace the best result. This log should never become persistent profile data or a second scoring channel.

Station ids, catalog ids, result activity ids, and evolution ids must stay the same string for a station. Seeds may change the prompt, objects, target rule, result copy, and NPC reaction, but they should not create extra badge identities or inflate reveal progress.

Accessory unlocks should be derived from session best results and station definitions in the first pass. Avoid adding separate save-state or wardrobe-state persistence until the visible reward loop proves itself.

Accessory display should use slot-based layers so characters improve visually without becoming cluttered. Initial slots: head, face, torso, back, hand, and sash. Show the newest earned accessory per slot, with ceremony-only rules for milestone items such as star robe and badge sash.

Accessories are visual/story rewards only, never career scoring modifiers. They can show progress on the avatar, feed reveal storytelling, and unlock ceremony styling such as badge sash or star robe, but career scoring must come from Career DNA trait results. This keeps the reveal explainable: the player gets paths because of what they practiced, not because of what they wore.

Add an `AvatarAccessoryLayer` system under `AvatarRuntimeView`. First pass should use child `SpriteRenderer`s with fixed local anchors rather than per-frame animated wardrobe art. Each accessory definition should include slot, sprite asset id, local offset, local scale, sorting offset, and ceremony-only flag. Accessories follow the avatar transform and flip with facing; the later full character art pass can tune offsets per avatar.

Reward rule: one core accessory per station in the first pass. Alternate seeds change story, prompt, objects, target rule, result copy, and NPC reaction, but they do not unlock separate accessories. Later seed expansions may add sticker variants or gallery flair, but not first-pass wearable rewards.

Milestone accessory rule: broader progress unlocks a small set of derived outfit milestones from unique completed activities, not from separate wardrobe state. At 3 unique completions, unlock the badge sash. At 5 unique completions, unlock an explorer cape or creator vest. At 8 unique completions, unlock a star robe or campus crown. At 10 unique completions, unlock a completionist reveal flourish that appears only in the reveal ceremony. These milestone accessories are visual proof of exploration, never scoring modifiers. The visual clutter rule still applies: show at most one visible accessory per slot, and ceremony-only items should not crowd normal campus play.

### Systems To Reuse

- Add a new `PartyStationController` as the reusable owner for station play. It should consume `PartyStationDefinition`, select/apply a seed, render the 4-6 object toy scene, evaluate the station rule, and emit a normal `MiniGameResult` through the existing room lifecycle.
- Add a small `ToyInteractionKit` layer so first-wave stations reuse interaction patterns instead of becoming six bespoke mini-controllers. It should build on the existing `Scripts/Interaction` primitives (`DraggablePiece`, `DropZone`, `DragFeel`, and `IDragDropHost`) and move shared drag/drop result types out of `DesignBuildController` if needed.
- `CareerQuestCatalog`: add or bridge station entries so gallery, campus, badges, and reveal stay aligned.
- `GameSession`: preserve best-result semantics and reveal readiness.
- `ActivityRoomController`: preserve enter/complete/return lifecycle.
- `ActivityResultEmitter`: keep one result emission per room lifecycle.
- `AchievementGalleryController`: render new badges from catalog data.
- `CareerRevealController`: add ceremony interpretation without replacing the scoring contract.
- `CampusEvolutionController`: add station city pieces, small ambient completion reactions, and reuse existing fanfare memory.
- `AssetCatalog`: add lightweight station props, accessories, city pieces, and badges.

Add validation tests that prove `CareerQuestCatalog`, station definitions, `CareerConfig` career scoring, and campus evolution metadata agree on playable ids. The current code already has a small split between catalog activities and career config activities; the expansion should close that gap instead of widening it.

Multiplayer contract: all 10 in-plan stations must be solo-playable and 2P-safe/shared-progress. Implement multiplayer at the `ToyInteractionKit` pattern level, not as 10 bespoke network systems. The host owns selected station seed, accepted submissions, progress, rejects, and completion. Clients submit actions; host validates; both clients see accepted progress. Do not sync per-frame drag positions. Partner presence can show as ghost/highlight/emote, not live mirrored dragging.

Multiplayer result read-model rule: host authority should remain the source of truth for recording `MiniGameResult`, but clients need more than `UniqueCompletedGames` to render the expanded reward surfaces correctly. Add a compact network read model for completed station ids plus minimal best-result summary data needed to derive accessories, combo cards, gallery/passport entries, reveal copy, and campus life reactions consistently on every peer. Do not replicate a full persistent profile, per-frame interaction data, or child-identifying history; replicate only session-scoped completion/reward facts derived from host-owned results.

`PartyStationController` should not directly mutate reveal, gallery, career ranking, or campus evolution state. Those systems should continue to derive from `GameSession` best results and station/catalog metadata, preserving the existing one-way progression spine.

Architecture decision: use Result-Spine Architecture. Station completion flows through one clean result path: `PartyStationController` -> `MiniGameResult` -> `GameSession` best result. Accessories, combo cards, reveal copy, gallery badges, and campus evolution derive from `GameSession` plus station metadata. Do not add direct side effects from station controllers to reward, reveal, gallery, or evolution systems.

Routing decision: new Party Pack stations should use generic station routing / catalog-driven dispatch instead of adding one enum value and one switch branch per station. Keep bespoke routes for major app states and existing core rooms if needed, but Party Pack entrances must route by `CatalogEntry.Id` / `PartyStationDefinition.Id` into the generic `PartyStationController`. `ActivityRoute` should remain a high-level app/legacy route concept, not the permanent identity model for every new station. `WorldAnchorEntrance`, `CareerQuestCatalog`, hub dispatch, app room mounting, instruction copy, and fallback anchors should all support station-id driven Party Pack entries. Adding station 11 later should mostly be content/metadata work, not edits across `ActivityRoute`, hub switches, instruction switches, app methods, and fallback anchors.

Add lightweight guided-run state to `GameSession` for the demo/PartyRunPresenter sequence. It should store ordered station ids, selected seed ids, current round index, completed station ids, and active/complete flags. This state is session-only and exists to survive route changes between campus, rooms, reward spotlights, and reveal during the guided/demo route.

Guided Party Run is resumeable by default when the player/demo has explicitly started it. Returning to campus, opening gallery, or visiting a non-run room should not erase an active guided run. Campus should show a clear Continue Party Run control while a guided run is active. Quit Party Run must be explicit and should clear only guided-run sequencing state, never earned `GameSession` results, accessories, badges, traits, or evolution pieces. Outside that guided route, the normal campus remains open-ended and free-choice.

### Anti-Pattern To Avoid

Do not extend the current hardcoded optional-room switch pattern into the new pack. A few hardcoded optional rooms were fine; a party campus pack needs a data spine or future content work will slow down immediately.

Also avoid building a full dress-up editor before the first playable reward loop works. Accessories should start as layered or badge-like overlays tied to results.

Code quality decision: make `OptionalRoomController` a thin bridge to `PartyStationController`, then retire its station-specific switches as the optional rooms are converted. Keep existing routing stable during the migration, but do not keep two permanent ways to define optional activities.

Existing/core stations remain playable. Future Career Cluster Pack hints may remain locked only if they are explicitly outside this plan's station list.

Hub entrance UX rule: remove the required "press E / Space / Return to enter" step for station doors. When the player avatar enters a station entrance area, the game should automatically enter that station. Use a short debounce/dwell and route cooldown so brushing an edge does not double-fire, but the player should not need precise positioning plus a key press. Update campus instructional copy accordingly: movement plus walk-into-door entry, not "Enter doors: E." Click-to-enter can remain as an optional convenience if it does not conflict with auto-entry.

Auto-entry guardrails: trigger only after the avatar remains inside an entrance for a small dwell window, roughly 0.15-0.25 seconds. After entering a station, ignore further entrance triggers until the new route is mounted. After returning to campus, apply a short grace period, roughly 0.5 seconds, before auto-entry can trigger. If future work returns the player near a specific door instead of central spawn, spawn just outside that entrance radius.

10-station campus layout rule: organize stations into readable districts rather than one crowded row. Keep enough distance between entrance radii so auto-entry zones do not overlap. Use larger visual markers/signs while keeping actual auto-entry radius controlled. Add a nearby highlight before auto-entry dwell completes so players know which station will open. Validate in `WorldAnchors` tests that no two entrance circles overlap. Final campus should show all 10 in-plan stations clearly, without tiny labels or door clutter.

Suggested districts:

- Core Quad: Design Build, Health Hero, Logic Court.
- First-Six Party Row: Robotics, AI Lab, Music, Kitchen, Vet, Game Studio.
- Wave 2 Edge: Weather, Spaceport, Newsroom, Green City.

Campus life reaction rule: completed stations should make the campus feel a little more alive beyond the city-piece skyline. Use small, derived reactions only: completed station buildings can glow, pulse, animate a sign, show the station guide waving/cheering, or add one small ambient prop near that station. Campus may show 1-2 ambient signs of progress at a time so it feels lively without clutter. Do not build a giant map rebuild, pathfinding crowd simulation, or persistent world-state system. Reactions derive from `GameSession` best results plus station metadata and should be deterministic enough for screenshots/tests.

Guided Party Run should require at least three unique activity completions before it routes to the reveal. A shorter run can return to campus or continue the sequence, but it should not bypass the existing reveal-readiness semantics. Normal play keeps the same rule: any three unique completed activities, in any order, can unlock the reveal.

Reveal richness thresholds for the final 10-station build: keep the reveal unlock at 3 unique station completions, but make the ceremony richer as more stations are completed. The reveal should use one content-driven presentation resolver, not separate bespoke cinematic systems per outcome.

## Station Seed Bible

Each station ships with one default seed and one alternate seed. A seed should feel like a fresh toy-room premise, but it must keep the station's core identity stable: same station id, same badge identity, same core accessory, same campus evolution prop, and compatible trait/career output. Alternate seeds change the prompt, objects, clue logic, NPC reaction, and micro-result copy; they do not create extra reveal progress.

Object count rule: each seed uses 4-6 interactable objects, with 5 as the default target. Use 3 core task objects plus helper, wildcard, reaction, or bonus objects so the room feels richer without becoming slow to build.

No-dead-toys rule: every listed interactable must do something visible. At least 4 objects per seed must participate in the core task or clue chain. `CoreTask`, `Clue`, and rule-driven `Meter` roles count toward that minimum. Any extra object must still react, animate, reveal a clue, change a meter, unlock bonus feedback, or affect the final micro-result. Do not list inert background props as interactables. Each object should declare a role such as `CoreTask`, `Clue`, `Helper`, `Wildcard`, `Reaction`, `Bonus`, or `Meter`.

Pacing rule: each station should be completable in roughly 45-75 seconds on a normal run. Richer object scenes should add delight, clues, reactions, and optional feedback, not mandatory slow steps. If a seed regularly takes longer than 75 seconds in smoke play, simplify the success rule before adding more art.

Hint ladder rule: every station needs a gentle, recoverable hint path. After idle time or a wrong attempt, show a small text or NPC clue. A second hint may highlight the relevant object, slot, bin, meter, or next step. Hints should guide attention, not solve the station outright. There should be no harsh fail state; the player can always recover and finish. In 2P shared-progress mode, accepted hints, highlighted objects, and progress state should be visible to both players.

Replay options rule: first play should enter the default station seed with normal pacing. On replay from campus or passport, the player may choose default seed or alternate seed when both are available. Demo/proof flows may request a `Quick` pacing option that shortens intro/fanfare text and uses the same validated seed mechanics; it is not a separate scoring tier. Do not add hard, advanced, timed-fail, or pressure modes in this plan. Reveal scoring, accessories, badges, combo cards, and campus evolution continue to use best result per station, not every replay attempt.

Station intro rule: every station starts with a very short theatrical beat before play begins. The intro should include one line of premise, one NPC or room reaction, a visible reward preview, and an immediate handoff to the toy challenge. Normal pacing should keep this to roughly 3-5 seconds. `Quick` pacing may compress it to a single line or skip straight to play while still showing the reward preview somewhere in the station UI.

Station guide rule: every station has one tiny guide identity or mascot voice. The guide gives the intro line, first hint, escalation hint, and success line. This is not a dialogue tree. Guide copy should be safe, encouraging, short, and data-driven from the station definition. Guides can be a person, room voice, robot, tool, or playful station mascot; first pass may render them as simple portraits, icons, or room labels rather than fully animated characters.

Shared juice pass rule: every station uses a small shared feedback kit so actions feel satisfying without bespoke animation systems. Correct actions get a small pop, sparkle, bounce, or friendly sound. Wrong actions get a gentle wobble, soft reset, or encouraging hint nudge, never a harsh buzz or shame cue. Station completion gets a short celebration. Accessory unlock gets the Accessory Spotlight cue. Combo unlock gets a distinct Combo Spark cue. Reuse shared effects/audio ids and keep station-specific flair to color, icon, guide line, and object reaction.

## Design And UX Rule

Use "weird nouns, grounded verbs" as the creative rule for the Party Campus Pack. The action should stay career-real: build, sort, diagnose, rescue, remix, match, compose, test, care, pitch. The scenario wrapper can be delightfully strange: lunchbox robots, bubblegum craters, thunderstorm parade beats, cosmic snack probes, dragon hiccups, courtroom spaceships, chef detectives, and tiny planet-neighbors.

This keeps the rooms creative without making the reveal feel arbitrary. A player should always be able to say, "I practiced building," "I practiced diagnosing," or "I practiced composing," even when the objects are playful.

## Station Content Rubric

Every station seed must pass this rubric before it counts as ready:

1. Grounded verb: the player practices a clear career action.
2. Weird noun: the scenario has one memorable playful object or situation.
3. Five-object toy scene: each station has 4-6 clear interactable objects, with at least 5 as the default target. Use 3 core task objects plus 1-3 helper, wildcard, reaction, or bonus objects so the room feels alive without making the success rule confusing.
4. No dead toys: every listed interactable has a visible role, and at least 4 objects participate in the core task or clue chain.
5. Quick party pacing: normal completion target is roughly 45-75 seconds.
6. Tiny guide voice: intro, hint, escalation hint, and success copy are short and encouraging.
7. Gentle hint ladder: idle or wrong attempts lead to recoverable clues and optional object highlights, never hard failure.
8. Trait fit: trait deltas match what the player actually did.
9. Career fit: career tags are explainable from the action.
10. Safe copy: strength-based, no destiny language, no scary/medical/legal pressure.

Bad example: "Click the magic button to become a doctor."
Good example: "Match the dragon's symptoms to a gentle care tool and comfort toy. You practiced Helping + Science."

- Every station has a short intro beat with premise, NPC/room reaction, reward preview, and immediate play handoff; quick pacing compresses it.
- Every station has a tiny guide identity or mascot voice with intro, hint, escalation hint, and success line.
- Every station uses shared juice feedback for correct actions, wrong actions, completion, accessory unlock, and combo unlock without bespoke animation systems.
- Every listed interactable has a visible purpose; at least 4 objects per seed participate in the core task or clue chain.
- Every station can be completed in roughly 45-75 seconds during normal play.
- Every station includes a two-level hint ladder, and 2P mode shares accepted hints/progress with both players.
- Every in-plan station emits a normal `MiniGameResult`.
- Every in-plan station unlocks one visible accessory.
- Milestone accessories unlock at 3, 5, 8, and 10 unique completions, with the 10-completion flourish reveal-only.
- The avatar can display at least three earned accessories by reveal time.
- Career ranking includes 30 reveal paths, with at least 12 directly station-backed in the first wave.
- Reveal includes superpower, career family, top paths, and hybrid identity.
- Reveal presentation styles support 3, 5, 8, and 10 completion thresholds plus combo/hybrid spotlight from the same `RevealSynthesis` path.
- At least 12 starter combo cards exist, validate their station ids, unlock only from completed best results, show a one-time lightweight Combo Spark after the second required completion, and pay off more fully in reveal/gallery.
- Gallery/passport shows badges, earned gear/milestones, unlocked combo cards, and recent station micro-results while staying session-only; completed badge/result entries can replay stations through the normal free-choice route.
- Campus evolution shows city pieces for all 10 in-plan station completions.
- Campus shows small ambient completion reactions for completed stations, derived from `GameSession` results, without a map rebuild or simulation.
- Existing three core rooms still count toward reveal and keep current behavior.
- Existing optional-room results still count toward reveal eligibility.
- No new flow asks for accounts, chat, profiles, or persisted child data.
- Guided demo route is optional and presenter-driven; it must not force normal free-choice players into a fixed station order.
- Campus station entry is automatic on entering the station area; final build should not require pressing E, Space, or Return to enter a mini-game.

## Not In Scope

- A giant map rebuild before the station pack works.
- Full procedural mini-game generation.
- Competitive scoring, leaderboards, rankings, or pressure-heavy multiplayer.
- Monetized cosmetics or collection pressure.

## What Already Exists

- `CareerQuestCatalog` already defines playable activity identity for campus, gallery, badges, and routes; the Party Pack should extend or bridge through it.
- `GameSession` already owns best results, Career DNA, reveal readiness, and career ranking; the Party Pack should add `PartyRunState` here and keep results session-only.
- `MiniGameResult` already carries activity id, display name, tier, source, time, accuracy, summary, and trait deltas; PartyStations should emit this same contract.
- `ActivityRoomController` and `ActivityResultEmitter` already provide room lifecycle and duplicate-result protection; `PartyStationController` should reuse both.
- `AchievementGalleryController`, `CareerRevealController`, and `CampusEvolutionController` already derive visual payoff from session results; the expansion should keep that derivation model.
- `AssetCatalog` already centralizes sprite/art lookup; first-wave props, accessories, badges, and city pieces should use the same pattern.

## Dream State Delta

This plan moves Career Quest Campus from a polished seven-activity slice toward the 12-month ideal of a living career campus. It does not attempt the full curriculum platform, teacher dashboard, procedural content, account system, or multiplayer mini-game depth yet. The delta is intentional: prove the reusable station spine, reward loop, and reveal upgrade first, then grow through Career Cluster Packs.
